## 一、P1：AI Agent 场景识别

[课程原文](https://datawhalechina.github.io/easy-data-x-ai/pm/P1%20%E8%AF%BE%E7%A8%8B%E7%A8%BF%EF%BC%9AAI%20Agent%20%E5%9C%BA%E6%99%AF%E8%AF%86%E5%88%AB.html)

本章讨论的重点是：**想应用 Agent 的场景，到底值不值得做、适不适合 Agent 化？**

### 1. 并非所有场景都需要 Agent

| 场景 | 优先考虑的方案 |
| --- | --- |
| 固定答案的 FAQ | 静态页面、搜索框或结构化 FAQ。 |
| 意图明确的结构化数据查询 | SQL、数据看板或 BI 工具。 |
| 对准确性零容忍的纯计算 | 确定性的计算公式或程序。 |

如果需求只是上面这些，用 Agent 可能增加出错环节、延迟和维护成本。若需求涉及模糊意图、外部工具/API 或复杂的持续交互，才更值得评估 Agent 的价值。

### 2. 立项前的三维度评估

| 维度 | 核心问题 | 具体检查 |
| --- | --- | --- |
| 数据可得性 | Agent 要用的数据存在吗？ | 数据在哪、是否准确、版本是否有效、有没有权限或接口获取。 |
| 任务可定义性 | 怎么样才算做对了？ | 有无事实锚点、可接受的输出边界、谁来评估。 |
| 流程编排的选择 | 控制权交给谁？ | 任务是否确定、错误代价多大、应采用 Agent 还是 Workflow。 |

**数据可得性是地基，任务可定义性决定能否衡量成功，流程编排决定可控性。**

#### 数据可得性：先问“数据在哪？”

课程给出的简单验证方法：列出 10 个希望 Agent 回答或解决的典型问题，逐一查找答案数据，检查它是否存在、准确，并且可以获取。

数据可能在文档、数据库、聊天记录里，也可能只在员工脑子里。即使数据存在，专门的管理软件也未必提供方便调用的 API；权限和接口同样是门槛。

如果多数问题的答案都拿不到，就应该先解决数据问题。

#### 任务可定义性：先想清楚“怎么验收？”

查订单状态有物流系统作为事实锚点，事实必须一致，表述可以不同。创意文案这类任务则受审美影响，不能只说“效果不好”，要先建立参考标准，可以采用多人打分、盲测或 A/B 对比。

#### 流程编排：先 Workflow，再 Agent

| 方式 | 控制权 |
| --- | --- |
| 自主 Agent | AI 根据目标决定下一步，选择工具和执行顺序。 |
| Workflow | 人预先设计步骤，AI 处理其中适合它的环节。 |

选择时问三个问题：

1. **数据可得性如何？** 数据分散、权限复杂时，先明确每一步怎样取得数据。
2. **任务的确定性高吗？** 大部分步骤确定时，优先 Workflow。
3. **错误的代价是什么？** 错误代价高时，把 AI 放在风险可控、可复核的环节。

Agent 与 Workflow 不是二元选择，而是一个控制权光谱：

**完全自主 Agent（AI 控制）←→ 人机协作 Workflow（混合控制）←→ 传统软件（人控制）。**

先跑通 Workflow，验证 AI 的价值，再逐步增加自主性，是更稳妥的路径。

> [!NOTE]
> **我的理解**
>
> Agent 功能立项想要做好：解决数据可得性，理清任务可定义性的标准，保守地先 Workflow、后 Agent。

### 3. Checklist 与本地 Agent

课程提供的 Agent 场景评估 Checklist，可以在评估需求时逐项检查，形成初步判断，并找到需要先解决的问题。

课程用“90% 的 Agent 功能失败，不是模型不够好，而是立项时没人问数据在哪”来强调数据的重要性。

> **整理补充（AI）**：这里保留作者的经验性说法，未核实统计口径，不作为已验证的行业比例。

对金融、医疗、法律和企业内部等数据隐私敏感的场景，数据能否交给系统使用，可能直接影响产品是否能落地，因此需要评估本地 Agent。

> **整理补充（AI）**：Agent 在本地运行，不自动等于“数据不出本地”。如果仍调用云端模型、搜索或其他外部服务，输入数据可能离开本机；需要检查完整的数据流和部署方式。

## 二、D1：大模型 API 基础

[课程原文](https://datawhalechina.github.io/easy-data-x-ai/dev/D1%20%E8%AF%BE%E7%A8%8B%E7%A8%BF%EF%BC%9A%E5%A4%A7%E6%A8%A1%E5%9E%8B%20API%20%E5%B7%A5%E7%A8%8B%E5%8C%96%E5%9F%BA%E7%A1%80.html)

本章以 **LangChain** 为框架，通过代码示例学习调用 Chat 模型、Streaming 和 Tool Use。

### 1. LangChain 与 Messages

LangChain 提供统一的模型接口、工具调用和流式处理，减少不同模型接口的适配工作。课程示例的关键写法：

| 写法 | 作用 |
| --- | --- |
| `init_chat_model()` | 初始化模型，通过 `model_provider` 指定提供商或兼容接口。 |
| `("role", "content")` | 用元组构建消息。 |
| `llm.invoke(messages)` | 调用模型，返回 `AIMessage`。 |
| `response.content` | 获取回复内容。 |

对话的本质是 **messages array**。在本课手动维护历史的示例中，每次调用都把所需历史放进消息列表，模型才知道上文。

```python
messages = [
    ("system", "你是一个简洁高效的技术助手。"),
    ("user", "什么是 RAG？"),
    ("assistant", "RAG 是检索增强生成，先检索相关资料，再基于资料生成回答。"),
    ("user", "它和直接把文档塞进 Prompt 有什么区别？"),
]
```

三类基础角色：`system` 提供行为说明，`user` 是用户输入，`assistant` 是模型回复。System Prompt 是控制 Agent 行为的重要入口。

> **整理补充（AI）**：这里讲的是课程示例的显式历史管理，不代表所有 API 或产品都要求客户端每次重传全部原始对话。历史也可以截断、摘要或由服务端管理；当前上下文与长期 Memory 仍要区分。

### 2. Streaming：逐步输出，改善等待体验

把 `invoke` 换成 `stream`，可以逐块读取内容：

```python
for chunk in llm.stream([
    ("system", "你是一个技术助手。"),
    ("user", "用三句话解释什么是向量数据库。"),
]):
    print(chunk.content, end="", flush=True)
```

课程强调面向用户的回答优先使用 Streaming，关注 **Time to First Token（首 Token 延迟）**，避免用户等到完整回答生成后才看到结果。

> **整理补充（AI）**：流式输出改善逐步呈现的体验，不保证总生成时间更短；要求完整校验后再展示的内容，也可能采用缓冲或非流式输出。

### 3. Tool Use：模型负责判断，代码负责执行

本课最重要的一点是：**模型输出工具调用意图和参数，外部程序才是真正执行工具的部分。**

完整链路：

1. 向模型提供可用工具的名称、说明与参数结构。
2. 模型根据问题，返回一个或多个 `tool_calls`。
3. 程序遍历这些调用，执行相应工具。
4. 程序用 `ToolMessage` 把结果传回模型，并对应正确的调用 ID。
5. 模型根据结果继续推理，可能继续调用工具，也可能给出最终回答。

模型是“指挥”，代码是“执行者”。工具能做什么、怎样执行、结果怎样处理，都需要开发者设计。

> **整理补充（AI）**：外部执行由程序负责，但模型也需要具备相应的工具调用能力，接口需要支持工具定义和结构化调用输出，因此不能把 Tool Use 理解为与模型能力完全无关。

### 4. LangChain 中的三个步骤

| 步骤 | 关键写法与检查 |
| --- | --- |
| 定义工具 | 用 `@tool` 装饰 Python 函数，写清函数名、docstring 和参数类型。 |
| 绑定并调用 | 用 `llm.bind_tools()` 绑定工具，检查返回的 `tool_calls`。 |
| 执行并回传 | 执行工具，用 `ToolMessage` 回传结果，再调用模型。 |

真实 Agent 往往需要重复这个循环，而不能假设一次调用就得到答案；要设置轮数等停止条件，避免持续调用而无法结束。课程后面的 `create_agent` 封装了这类循环。

如果模型没有调用工具，可以先检查工具 docstring 是否写清楚“在什么情况下使用”，以及参数和用途是否明确。

> **整理补充（AI）**：未调用工具不一定都是 docstring 的问题，还应检查模型是否支持、接口是否兼容、工具是否成功绑定，以及当前问题是否真的需要工具。

### 5. 与上一课的联系

Tool Use 把模型推理与外部数据、执行能力连接起来：查知识库、存记忆、调用外部服务，都可以经由工具完成。

> **整理补充（AI）**：这是本课 Agent 示例的实现路径，不代表所有 RAG、Memory、Skill 或 MCP 系统都必须由模型主动发起 Function Calling。例如，应用也可以先固定检索，再把结果放进上下文。

### 1. 这节课主要解决什么问题？

**模型负责推理，数据库负责可靠保存、查询和恢复状态。** Agent 不只是保存聊天记录，还要管理业务数据、文档与向量、记忆、任务状态、工具结果和权限。

AI 原生数据库也不是“装了一个大模型的数据库”。课程从六个方面观察它的能力：多类数据、混合检索、事务与恢复、模型调用、Agent 工作流、交付形态。

### 2. 先记住四组关系

| 概念 | 预习时先抓住的重点 |
| --- | --- |
| 关系、文本、向量、JSON 等数据 | 同一份业务事实有不同表达方式，分别服务于精确过滤、关键词检索、语义检索和动态属性管理。 |
| 混合检索 | 组合向量召回、全文召回与业务过滤，再融合排名、按需重排；“语义相关”之外，还要满足权限和有效性要求。 |
| 事务、日志与恢复 | 保持相关业务状态一致，在故障后恢复；异步索引还可能导致数据已写入、却暂时搜不到。 |
| Fork / Diff / Merge | 在隔离分支试写，查看变化，再决定合并或丢弃；沙箱不能替代权限和审核。 |

### 3. 数据库内 AI 与部署选择

课程以 seekdb 为例介绍 `AI_EMBED`、`AI_RERANK`、`AI_COMPLETE`，分别用于嵌入、重排与生成调用。基本顺序是：

**先过滤 → 再召回 → 缩小候选集 → 最后重排或生成。**

嵌入式模式适合个人知识库、桌面和离线应用；服务器模式适合团队服务与集中管理。统一数据库可以减少跨系统同步和治理成本，但不代表所有场景性能都更好，仍要根据规模、并发、一致性和运维要求比较。
